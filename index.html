How It Fits Together

What Sharding Means Here

A tickerplant is single-threaded. It logs every message and then publishes it, so one TP has a hard ceiling on rows per second. Sharding splits the symbol universe horizontally so that each shard runs a complete, independent tick chain over half the names. Two TPs double ingest capacity, and a slow consumer in one shard can't back up the other.

The cost is that no single process sees everything. The gateway has to route single-symbol queries to the right shard and fan out and merge cross-symbol ones. The first-letter shard key is simple but can be uneven, because the busiest names may cluster in one half of the alphabet.

Trade-offs

Sharding works well up to a point, but teams often run into new problems as volume grows. The notes in grey point to where each one shows up in this repo.

Advantages

  • Builds on existing tickerplant knowledge, so there's little to learn. tick.q is vendored unchanged.
  • Needs only a modest amount of extra kdb+ code. wdb.q, idb.q and config.q total about 260 lines.
  • Consumers see a single logical data source. Everything goes through the gateway on 5030.
  • A good balance of throughput and simplicity at moderate scale. Two TPs double the ingest ceiling.

Limitations

  • Natural ways to split the data get harder to find as volume grows. A first-letter split is uneven when the busiest names cluster.
  • Operational complexity grows with each shard. Every shard adds four processes, four ports and a segment.
  • It isn't designed to span machines, so you hit a vertical scaling limit. Everything is on localhost, and all segments are local paths in par.txt.
  • Coordinating end-of-day write-down eventually becomes a scaling problem. The HDB's -shards barrier waits for the slowest WDB's merge.

As scale and operational complexity grow, a more advanced architecture may serve you better.

Keeping the RDB and IDB in Sync

Every row has to be visible in exactly one tier as it moves from the RDB to the IDB. Two designs handle this differently:

Tick-X: the flushed watermark W. Every row with time < W is already persisted to the IDB. On each flush, the main RDB writes W to a file and asks the tickerplant to broadcast it, using broadcastWatermark:{[w] if[count shedSubs; (neg shedSubs)@\:(`.rdb.shedTo;w)]}. The chained RDB then sheds everything below W and keeps only the unflushed tail.

The broadcast goes through the TP, not a direct connection, because the chained RDB receives its data from the TP on one ordered connection. By the time .rdb.shedTo[W] arrives, every row it covers has already arrived too. A side channel could overtake a row still in flight, and that row would land after the shed and never be cleaned up.

W also acts as a flush floor. After a restart the RDB replays the whole day from the TP log, but it drops everything below W before each flush. Rows already on disk are therefore never written again, which makes restarts idempotent. The blueprint's WDB has no such floor, which is why Lab F warns against restarting it mid-day. Variant F+ adds one, together with a log position.

Blueprint: a handshake. No watermark, and the TPs carry no control messages, which keeps ordering simple across two of them. The WDB signals the IDB and the RDB directly. In the version the KX article describes, the RDB purge goes out only after the IDB confirms its reload. The current main sends both signals async with the purge first, which leaves a brief gap; Lab G measures it and patches in the confirmed version.

Event-time cutoff. The WDB computes cutoff from the newest event time in memory minus 5 minutes, not from .z.p. For a live feed the two are nearly the same. During a 100× replay they're far apart, and only the data's clock makes sense.

FEED

Synthetic TAQ bbo and trade generator. It routes each row by the first letter of its symbol and fires end of day on both TPs at the close of each simulated session. One process, no port.

TP

Appends every update to its log file sym<date>, then publishes it to subscribers. It holds no data. One per shard.

RDB

First subscriber. It keeps only the last few event-minutes in memory and serves real-time queries. It never touches disk, and its end of day only clears tables.

WDB

Second subscriber, and the only process that writes intraday. Every 10 s it writes rows older than 5 event-minutes as an int-partition under today/<i>/. At end of day it merges those into a sorted date partition.

IDB

Loads the WDB's int-partitions into memory and serves earlier-today queries through the same selectFunc API as the RDB and HDB. It grows all day and empties at end of day.

HDB

A single process over a segmented database. par.txt lists both segments, and the HDB reloads only after both shards have finished end of day.

GW

Routes by symbol to one shard's RDB and IDB, or fans out to every tier including the HDB, then merges the results.

What "Shard-Aware" Means

The gateway loads the same shard function as the feed and keeps a handle to every tier of every shard. With a symbol hint, .gw.route sends the query only to that shard's RDB and IDB. Without one, it fans out to every tier and combines the results with raze, which is safe only because the tiers never hold the same rows. It falls back to the HDB after end of day, and it carries on if an IDB is down. A vanilla gateway asks every process every time.

There's a trap in shardedgw.q: .gw.lastTrade[sym] passes an empty hint, so it actually fans out to both shards. Only .gw.lastTradeH[sym;hint] routes. The functions tradeStats and tradeCountByShard always fan out to every tier, HDB included.

The Five Rules

AquaQ's kdb+ Architecture Workshop (Jonny Press and Jamie Grant) ends with five rules for real-time kdb+ systems. They make a good lens for this blueprint: each rule explains a choice it made, or a place where it stops short. The labs teach the blueprint as shipped. The variants after them each fix one rule, on a copy, without touching the repo.

1

Keep All Messaging Asynchronous

A synchronous call blocks the caller until the other side answers, so a slow or dead peer stalls you, and everyone waiting on you. The TP publishes with neg h and never waits for a subscriber. The hard case is the gateway: most clients ask synchronously, so the gateway itself has to answer later instead of blocking.

2

One Job per Process

A process with two jobs does both badly at the moment they collide. Plain kdb+tick's RDB serves queries and writes the day to disk. At end of day it stops reading from the TP, becomes a slow consumer, and needs up to 4× the day's data in RAM while it writes (AquaQ's figure). How close it gets depends on how it writes: sorting the whole table in memory, enumerating symbol columns, and power-of-two allocation each add copies.

3

Offload Frequently Run Queries

If many users poll the same calculation, compute it once, incrementally, in a dedicated real-time engine (a CEP) that subscribes to the TP or a chained TP. Each request becomes a lookup in a small keyed table instead of a scan of the RDB. Latency-sensitive values, such as an alert when the book skews, belong there too.

4

Replicate for Resilience and Concurrency

Lightweight processes such as HDBs, gateways and CEPs should be cheap to restart, constrained so a bad query can't take the host (-w, -T), and run in several copies so one long query or one crash doesn't block everyone. Every process should be restartable without corrupting anything.

5

Use Gateways for Transparency

Clients talk to one entry point. Routing, load balancing, failover and permissions happen behind it, so a process can die or move and the client doesn't notice.

BThe WDB Flush

Run in WDB0shell

Every .wdb.flushMs (10 s), .wdb.flush runs these steps:

  1. Set cutoff to the maximum event time minus .wdb.intv (5 min).
  2. Enumerate rows older than cutoff against the shared data/hdb/sym with .Q.en.
  3. set them to today/<i>/<table>/ with g#sym, then drop them from WDB memory.
  4. Send .rdb.purge[cutoff] to the RDB and .idb.reload[] to the IDB, both async.

After log replay the WDB has cd'd into data/segment0/sym, so `:today is a relative path into its own segment.

/ WDB0 tab
q).wdb.intv, .wdb.flushMs        / 5 (event-min retention), 10000 (ms timer)
q)system"cd"                     / …/data/segment0/sym
q).wdb.i                         / next int-partition number
q)key `:today                    / `0`1`2… written so far
q)select n:count i, lo:min time, hi:max time from trade   / ≤ 5 event-min held
q).wdb.flush[]                   / force a flush now, then re-run key `:today
q)count get `:today/0/trade      / read one int-partition back
ls data/segment0/sym/today                    # 0 1 2 …
ls data/segment0/sym/today/0/trade            # one file per column (splayed)
du -sh data/segment{0,1}/sym/today            # disk used today, per shard

CThe IDB and the RDB Hand-off

Run in CTRLIDB0

.idb.reload refreshes sym and inserts only the int-partitions that aren't in .idb.loaded yet. That keeps each reload cheap and preserves g#sym. The IDB holds today in memory rather than memory-mapping it, which is why it grows all day.

The IDB's newest row should be older than the RDB's oldest row. Each row lives in exactly one tier, so the gateway can raze the results without double-counting.

Both signals are async. For a moment after a flush, a slice can be missing from both the RDB and the IDB. The code accepts that trade-off so a slow IDB can never stall the flush timer.

/ CTRL tab, in q
q)r0:hopen 5011; i0:hopen 5015
q)q:"select n:count i, lo:min time, hi:max time from trade"
q)(`idb`rdb)!(i0 q; r0 q)          / idb hi < rdb lo
q)i0".idb.loaded"                  / int-partitions already in memory
q)i0"selectFunc[`trade;.z.D;.z.D;`AAPL`MSFT]"   / same API as RDB and HDB
q)(r0;i0)@\:"`long$1e-6*first system\"w\""       / MB in use: RDB flat, IDB grows
/ IDB0 tab: force a reload and watch the log line
q).idb.reload[]                    / "IDB loaded: +0 new (n total)"

DThe Segmented HDB

Run in shellHDB

data/hdb holds only par.txt and the shared sym file. The data lives in the segments, and each segment holds the same dates for its own half of the symbols. kdb+ reads both segments as one table.

Because both WDBs enumerate against the same data/hdb/sym, a symbol has the same enum index in every segment.

The HDB is empty until the first end of day, about 4 minutes after the feed starts.

EEnd of Day and the Merge

Run in CTRLshell

The feed calls .u.endofday[] on both TPs at 16:00 event time. You can also trigger it yourself. What follows:

  1. TP sends .u.end d to every subscriber, moves to d+1, and rotates its log.
  2. RDB clears its tables. Nothing is saved.
  3. WDB flushes the remainder, then razes today/* per table, applies `sym xasc and p#sym, writes <date>/<table>/, and deletes today/.
  4. WDB sends .hdb.eodReload to the HDB and .idb.reload[] to the IDB. The IDB finds no today/ and empties.
  5. HDB counts the reports and runs \l . once both shards have arrived.

Always end-of-day both TPs. If only one does, the HDB waits forever for the second report. Each EOD also moves the TP date forward a day, so partitions run ahead of the calendar. That's expected in this demo.

Variant E+ hands the sort to one worker per table, so the WDB never stops reading the feed.

GThe Tier Hand-off: Gap or Confirmed

Run in CTRLWDB0

The "failover" in the Tick-X comparison is this hand-off: the moment a slice of rows leaves the RDB and becomes visible in the IDB. The blueprint's code does it like this:

/ sharded/wdb.q, end of .wdb.flush
.wdb.sigRDB[cutoff];   / async: RDB, drop rows < cutoff
.wdb.sigIDB[]          / async: IDB, load the new partition

Both calls are fire-and-forget, and the purge goes out first. Until the IDB finishes loading, the rows just below cutoff are in neither tier.

In Tick-X, the watermark travels through the tickerplant itself. Every subscriber therefore sees it in the same order as the data, and no gap can open.

The confirmed version swaps the gap for a brief overlap. Rows sit in both tiers until the purge lands, and the WDB's flush now waits on the IDB. That trade-off is why the authors chose async.

1. Catch the gap. This sampler polls the RDB first and the IDB second, every 20 ms. Rows moving between the two reads can only shrink the measured gap, so anything it records is a real gap. In a steady state, the RDB's oldest row sits right after the IDB's newest one.

/ CTRL tab, in q: one statement per line
q)r0:hopen 5011; i0:hopen 5015
q)gaps:([]t:`time$();rlo:`timespan$();ihi:`timespan$();g:`timespan$())
q).z.ts:{rlo:r0"exec min time from trade"; ihi:i0"exec max time from trade"; if[0D00:00:01<g:rlo-ihi; `gaps insert (.z.t;rlo;ihi;g)]}
q)\t 20
/ …wait about a minute (about 6 flushes)…
q)\t 0
q)gaps                                   / one burst of rows per flush
q)select n:count i, worst:max g from gaps   / g ≈ one flush of event time

2. Make the hand-off confirmed. Wrap the purge so that the WDB first makes a synchronous .idb.reload[] call and sends the purge only after it returns. The original async .wdb.sigIDB still runs afterwards; it finds nothing new and does no harm. End of day is untouched.

/ WDB0 tab
q).wdb.sigRDB0:.wdb.sigRDB                      / keep the original
q).wdb.sigRDB:{[cutoff] if[.wdb.idbH<=0;.wdb.idbH:hopen .wdb.idb]; .wdb.idbH".idb.reload[]"; .wdb.sigRDB0 cutoff}
q)\t .wdb.flush[]                               / ms per flush now includes the IDB load

3. Re-run the sampler from step 1, starting from gaps:. The table should stay empty. To go back to the original behaviour:

/ WDB0 tab
q).wdb.sigRDB:.wdb.sigRDB0

Ignore rows logged around an end of day, when one tier is empty and the subtraction is meaningless.

There's no hot standby in either design. Recovering from a crashed process means restarting it and replaying the TP log, as in Lab F.

IA TP Log That Says How Far It's Safe to Read

Run in CTRL

From Mindfruit: Shared Memory Tickerplant Log Files. If the TP log itself is the transport, for example in shared memory instead of TCP, readers need a safe way to know how much has been written. A growing file size isn't enough: a reader can see the new length before the write behind it has finished. That's the same reason readers of a normal TP log must not read past .u.i.

The trick is to make the first message in the log a kdb+ call, (`.mg.hdr; offset). Its 64-bit value always lands at byte 24, which is 8-byte aligned and on the first page. After each append, the writer overwrites it with the offset of the newest message. Readers can poll those 8 bytes.

Because the header is just another message, -11! still replays the file. A replaying process only needs a dummy .mg.hdr. Live subscribers would need custom reading code.

The blueprint's TPs don't do this. To use it here, tick.q would write the header at log rotation and update it after each upd, and RDB and WDB replay would define .mg.hdr:{}. The article updates the value through mmap or io_uring. This lab rewrites the whole file with 1:, which is fine for a demo only.

/ CTRL tab, in q: 1. write the header message
q)L:`:/tmp/mg.log; .[L;();:;()]; h:hopen L
q)h enlist (`.mg.hdr;0x0 sv 0xbebafecaefbeadde)
q)read1(L;0;32)          / ff01000000000000 000002000000 f5 2e6d672e68647200 f9 deadbeefcafebabe
q)0x0 sv reverse read1(L;24;8)   / the value at byte 24 (stored little-endian)
/ 2. append ordinary upd messages, then move the marker
q)o:hcount L; h enlist (`upd;`trade;([]sym:`AAPL`MSFT;price:189.5 411.2))
q)o:hcount L; h enlist (`upd;`trade;([]sym:enlist`NVDA;price:enlist 121.4))
q)L 1: @[read1 L;24+til 8;:;reverse 0x0 vs o]   / marker = offset of newest message
q)0x0 sv reverse read1(L;24;8)                  / equals o
q)read1(L;o;hcount[L]-o)                        / raw bytes of the newest message
/ 3. replay with -11!: only a dummy .mg.hdr is needed
q).mg.hdr:{[o] -1"header: newest message at byte ",string o;}
q)upd:{[t;x] -1"upd ",string[t]," rows=",string count x;}
q)-11!(-2;L)             / 3 messages: header + 2 upd
q)-11!L                  / prints the header line, then both upd lines
q)hclose h; hdel L

F+Restarting the WDB from a Checkpoint

Extends F · Rule 4 · Run in shellCTRLWDB0
Changes vs blueprint New variants/wdbck.q, a copy of wdb.q with checkpoints. WDB0 runs the copy.
Revert rm -rf variants, then restore the launch configuration (last line of the second block).

The problem. Restart WDB0 mid-day and it replays today's TP log from message 1, resets .wdb.i to 0, and flushes everything below the cutoff into a new today/0. The partitions written before the crash are still on disk, so end of day merges those rows twice. The IDB has already loaded a partition named 0, so it never reads the new one. McCarthy's w.q sidesteps this by deleting its temp data and replaying the whole day, because it's "difficult to locate the point in the TP log which was last committed to disk". This variant records that point.

The idea, from KX RT. RT hands each subscriber message to upd[msg;pos]. The subscriber stores the position next to its own state, and on restart it asks RT for the stream from that position. RT keeps nothing per subscriber. A tickerplant has no position to hand out, but in this repo the TPs run without -t, so a process subscribed to every table gets exactly one message per log entry. Counting upd calls gives the log index.

What gets stored. After each flush the WDB writes today/ckpt:

  • safe: the first message that still has a row at or above the cutoff. Every message before it is fully on disk.
  • cutoff: the flush watermark, the same idea as Tick-X's W.
  • upto: how many messages had arrived. Only these could have been flushed, so the cutoff filter applies to them alone, and a late row that arrives afterwards is kept.
  • The last partition number and the log file name.

On restart the WDB skips safe−1 messages, drops rows below the cutoff in messages up to upto, and replays the rest in full. New partitions are numbered after the highest one on disk. A partition newer than the checkpoint means the WDB died between writing data and writing the checkpoint, so it's removed and rebuilt from the log.

The checkpoint lives in today/, so end of day removes it along with the data. The IDB and the EOD merge read today/ckpt/trade as missing and skip it. A checkpoint for a different log, because the WDB was down over an end of day, is ignored, and the WDB falls back to a full replay.

This code is untested. With -t the TP batches, positions stop matching the log, and you'd checkpoint .u.j instead. Avoiding Duplicates, and Removing the Ones That Get Through

F+ stops a restart from writing rows twice, but two gaps remain. If the WDB dies after writing a partition and before writing the checkpoint, the partition is an orphan that F+ deletes and rebuilds. A late row that arrived after the last checkpoint is replayed and written again. Option A closes the first gap in the write path. Option B catches whatever is left at end of day.

A. Make the writes idempotent. Name each partition after the 5-minute event-time bucket its rows fall in, and align the cutoff to that grid. A replay then produces the same rows under the same name, and writing them again overwrites instead of adding a copy. The orphan case heals itself. Rows for a bucket the checkpoint already vouches for, or one this process has already written, are appended rather than overwritten, so a late row never wipes a closed bucket. The checkpoint goes to ckpt.tmp and is renamed into place, so a crash can't leave half a file.

H+Hard Limits: -w, -T and -g

Extends H · Rule 4 · Run in HDBRDB0CTRLnew q

Rule 4 says lightweight processes should be constrained and allowed to fail, then restarted. Lab H's -maxmb is the gentle version: the RDB drops batches and stays up. kdb+ also has hard limits, which suit processes that are cheap to restart.

  • -T stops any single client query after N seconds with 'stop. It fits HDBs and gateways, where one runaway query otherwise blocks every other user.
  • -w caps the heap in MB. Going past it is a wsfull, not a dropped batch. It fits processes that can be restarted cheaply, not a TP or an RDB holding the only copy of today.
  • -g 1 returns memory to the OS as soon as it's freed. Under the default -g 0, an RDB's heap stays at its peak after every purge, which the OS and your monitoring see as a leak.

A hard limit only helps if something restarts the process. In production that's a supervisor such as systemd, supervisord or TorQ's launcher. Step 4 shows the idea with a shell loop.

The -w behaviour shown follows the workshop deck. The KX reference documents the limit but doesn't say whether the process exits, so check yours. -T applies to client calls, not to timers or the console.

J+Recovering a CEP Without the Log

Lab J's CEP starts empty, so after a restart its VWAP is wrong until the next day. It could replay the TP log like the RDB does, but that's slow, and it needs the TP's filesystem, which ties the CEP to that machine.

TorQ's answer is to recover from the RDB. The TP counts rows per table, a subscriber gets that count N when it subscribes, and it asks the RDB for where i<N. That doesn't work here, because the sharded RDB purges after every flush: its row i isn't the TP's row i, and the older rows are in the IDB.

So this variant uses a watermark the data already carries. tradeId rises in publish order within each shard. The TP remembers the highest id it has published, and returns it in the same call that subscribes the CEP. Every trade at or below it is in IDB + RDB, and every trade above it arrives live. The CEP waits for the RDB to reach the watermark, snapshots both tiers, and then drops live rows at or below it.

This is untested. The one gap is the hand-off in Lab G: if a flush purges RDB rows before the IDB reloads them, the snapshot misses them. It needs a key that rises in publish order. bbo's seq works the same way, but a real feed with per-source sequences needs one watermark per source.

K+An Async Gateway

The blueprint gateway runs each request to completion. .gw.tradeStats calls every tier with a sync h q, so while one client's HDB query runs, every other client waits, even for 1+1. Most clients, such as q consoles, Studio and dashboards, ask synchronously, so you can't fix this on the client side.

The fix is deferred sync. The gateway takes the sync request, sends the work to the tiers async with a callback, and marks the reply as deferred with -30!(::). Then it goes back to serving other clients. When every tier has called back, it combines the results and releases the original caller with -30!(handle;0b;result). If a tier fails, the error is passed through with -30!(handle;1b;msg).

The tiers need no new code: each request ships a small lambda that runs the query and calls .gwa.back. P9 uses the same -30! mechanism for the TP log handshake.

This is untested, and it needs kdb+ 3.6+. A tier that never answers leaves the client waiting forever, so a production version adds a timeout sweep on .z.ts. The stock .gw.* functions on 5031 are still sync, and only .gwa.* are async. Sleeping the HDB also delays any end-of-day reload that arrives meanwhile.

Production Patterns

What a production stack adds around the blueprint, mostly from AquaQ's architecture workshop. These are notes rather than labs, because most of them need more than one machine. The Fuller Tick Stack table in Context, Comparisons & Practicalities shows where each piece would plug in.

Splitting Tickerplants

The blueprint splits by symbol, and Sharding by Data Source shows splitting by data source. Other common splits are by asset class, region, table, or business use (trading vs research). Any process below a TP can be striped the same way, for example an RDB for trades and another for quotes.

  • One shared HDB, as here: every WDB writes into one database, which needs a shared filesystem. Splitting by table is easiest. Splitting by instrument needs a segmented HDB, which is this blueprint.
  • Separate HDBs per asset class or region, joined in the gateway: no shared hardware, but harder for users, who now need the gateway for any cross-database query.

Prefer splitting by instrument over splitting by data type. Keeping all of IBM's data in one database beats putting its trades in one and its quotes in another, because most queries join them.

Where the End-of-Day Write Happens

Where the end-of-day write happens decides how much memory you need and whether data is ever unavailable.

Compression

Columns compress one file at a time and decompress transparently on read. Repetition decides the ratio: symbols compress very well, timestamps hardly at all. Choose per column, weighing ratio against read and write speed on your disks.

  • Don't compress intraday temp data. EOD rewrites it anyway, so you would pay the write cost twice.
  • Compress at EOD, or leave EOD fast and compress older partitions at the weekend, in parallel.
  • Data in memory is never compressed, so an RDB uses more memory than the same day on disk. IPC messages can be compressed in transit.
  • Filesystem compression, such as ZFS, can beat kdb+'s own, and hardware accelerators help further.

Gateways at Scale
  • Load balancing: several HDBs mount the same par.txt, and the gateway sends each query to a free one. If one dies, clients don't notice.
  • Stacked gateways: each cluster of identical processes gets a balancing gateway, and master gateways merge across the clusters. Masters can be replicated, and a balancing gateway can still be used directly.
  • Quick and slow pools: separate HDB pools for interactive queries and long reports, so a report never queues ahead of a user.
  • An authentication service that the gateway asks before forwarding a query.
  • All of it needs the async gateway from K+. A sync gateway can only serve one query at a time, whatever sits behind it.
Disaster Recovery
  • Hot-hot: two identical, independent stacks, each with its own feed. Users can query either one, which doubles capacity, or just one, which tells you whether a single site can carry everyone.
  • Hot-warm: the DR site runs only feeds and TPs, and the rest starts at failover. Its logs stay current, but the RDBs and HDBs have to load before users can query.
  • Hot-cold: nothing runs until failure, so recovery is the slowest, and anything since the last copy of the data is lost.

Client failover is manual switching, retry logic in the client API, or a proxy, virtual IP or load balancer.

When the TP dies, the RDB and WDB recover from the log, but the TP can only recover messages it was never sent if the feed handlers log locally and can replay into it. The usual answer is to fail over to DR and rebuild the primary after end of day.

Access Control
  • Start simple: -u/-U with a password file, run q as an unprivileged user, -b to block writes from clients.
  • .z.pg:{reval x} evaluates client queries read-only. .z.pw checks logins.
  • TorQ's permissioning adds authentication (hashed local passwords or LDAP), roles for what a user may run (free-form selects, stored procedures with parameter checks), hierarchical groups for which tables they may read or write, and "virtual tables" for row-level filters.
  • Enforce it in the gateway, the only process clients reach. In the blueprint that's shardedgw.q.
Discovery

Instead of ports hard-coded in scripts, each process registers its type, host and port with a discovery service when it starts. Others ask for "all RDBs" and get notified when a new one registers, so capacity can be added while the system runs. The discovery service can be replicated too. Here, ports live in up-sharded.sh, the Warp YAML and the gateway's flags.

Monitoring and Support
  • Standard checks for every process (CPU, memory, I/O), fed into the firm's usual tools such as Geneos, Zabbix or Nagios.
  • kdb+-specific checks: pingbacks, slow subscribers (.z.W), sym file growth, table row-count growth rates, and HDB save-down complete.
  • A central ops database, itself a tick stack, that every process publishes logs, errors, query stats and heartbeats into. Use it for long-term usage patterns and capacity planning. P1's collector is a small start.

Slow Subscribers: Causes and Fixes

A subscriber is slow when it reads from its socket more slowly than the TP writes to it. The TP never blocks on a subscriber, so the bytes wait. First they fill the kernel's TCP send buffer. After that they queue in the TP's own heap, per handle, and that queue is what .z.W reports. It isn't the TCP buffer, which is why tuning TCP buffers barely helps. If it keeps growing, the TP runs out of memory and every subscriber loses its feed, not just the slow one.

q)k!{x"(.z.f;system\"p\")"} each k:key .z.W   / sync calls from the TP: only while debugging
/ P1's collector already records this every 30 s, in .perf.stats
/ subscriber: buffer in upd, apply on a 100 ms timer

\t 100
.u.end0:.u.end; .u.end:{.z.ts[]; .u.end0 x}   / apply what's buffered before end of day

P7Pausing and Resuming a Slow Consumer

P8Log Format: Appended vs Memory-Mappable

The blueprint's TP appends to its log with a file handle (l enlist (`upd;t;x)). get on such a file copies the whole day into the heap, and -11! can only replay from the start.

The Debate: Is Logging the TP's Job?

The comment threads under Alvi Kabir's posts are worth reading before you adopt any of P4 or P7. The disagreement is about what a tickerplant is for.

For decoupling (Alvi Kabir)

  • Distribution is the TP's primary job. The faster it ticks, the sooner every consumer and client sees data.
  • Logging adds a failure point to the TP, such as a stalled filesystem or a corrupt file. Taking it out leaves the TP small and hard to break.
  • A dead tplogger doesn't stop the plant. A supervisor like supervisord restarts it, which is no worse than today's single point of failure in the TP.
  • Pause/resume with offset replay keeps a slow subscriber connected and current, where today the only options are to disconnect it or restart it and replay the whole day.

Against, or with caution

  • Jonny Press (Data Intellect): the TP's primary purpose is logging. Separating the log from the TP makes failure scenarios hard to manage. The sleep in .u.rep is a race, because under load the logger always trails the TP and nobody knows how long to wait.
  • Alex R: what if the tplogger never starts, stalls, or errors mid-write? Should the TP stop publishing? What does "operational" even mean for a logger?
  • Conor Mahony: memory-mapping huge logs has OS risk, and paused subscribers may just flap. An upstream in-memory broadcaster feeding fast aggregation engines, with plain tick behind it for capture, may suit better.
  • Conor Mahon: the speed comes at the price of not guaranteeing complete data if the logger bounces.

Ideas from the thread for closing the gaps:

  1. Replace the sleep with a deferred sync handshake: client → TP → logger → TP → client. It's deterministic and accounts for buffering (Conor Mahon). There's a sketch in P9.
  2. When the tplogger disconnects, have the TP fall back to logging inline, and hand logging back when the logger resubscribes (Maurice Lim).
  3. On startup the logger must validate the log and truncate it to the last good message, using -11!(-2;file) as tick.q's .u.ld does (Alvi Kabir).
  4. Segment logs by table and period, like TorQ's STP tabperiod, so a subscriber replays only the tables and hours it needs and drops the duplicates it already holds (Jeremy Lucid).
  5. Keep logging in the TP but flush to disk only on publish, as TorQ's STP batching does. Throughput rises, at the cost of latency jitter and a small loss window (Jonny Press).
  6. For high availability rather than speed, KX Reliable Transport (RT) replaces the TP with a Raft-replicated log (Daniel Walsh, KX).

P9Replacing the Sleep with a Deferred-Sync Handshake

Run in fast stack

The fast RDB's replay polls the log every 10 s, up to 5 times. Instead, the RDB makes one sync call to the TP. The TP defers its reply with -30! and asks the logger to call back once everything up to the TP's current .u.i is on disk. When the logger does, the TP releases the RDB and its replay starts.

There's no fixed wait and no guessing. The logger flushes before it acknowledges, so the RDB never replays a log that is still being written.

This is an untested sketch. -30! needs kdb+ 3.6+. While the RDB is blocked in the sync call, live updates may already be arriving on the same handle, so rows can land ahead of the replayed ones; buffer or sort them if order matters. A logger that never answers blocks the RDB, so a production version needs a timeout.

Sharding by Data Source Instead of Symbol

Suppose TP0 carries everything from ds1 and TP1 everything from ds2. Only three parts of the repo know how rows are split: the shard key, the feed and the gateway. The TP, RDB, WDB, IDB and HDB never look at sym; they store and move whatever arrives, so they don't change.

1. The shard key (sharded/config.q): look the source up instead of testing the first letter. A source missing from the map comes back null, so the feed can reject it rather than guess.

.cfg.src2shard:`ds1`ds2!0 1;
shard:{.cfg.src2shard x}           / was: first letter in A–M → 0, else 1

2. The schema (tick/sym.q): add a source column. tick.q requires time and sym to be the first two columns, so src goes third.

  time:`timespan$();
  sym:`g#`symbol$();

  ex:`char$();

3. The feed. The simplest option is one feed handler per source, each connected only to its own TP, with no routing at all. If one feed carries both sources, route on the new column:

The .u.rep directory trick. After replay, an RDB or WDB runs cd on the log path minus its last 10 characters, the date. data/segment0/sym2026.10.18 becomes data/segment0/sym, which is exactly the segment directory that par.txt lists. That's why the WDB can write to the relative path `:today, and why the TP's schema name "sym" is also the segment's folder name.

Replay needs the log on the same host. r.q replays .u.L straight from disk, so a subscriber on another machine would need the log copied or shared. This is another reason the blueprint is single-host.

End of day ignores the real calendar here. .u.ts checks .z.D against .u.d every second. Because the feed calls .u.endofday[] every simulated session, .u.d runs ahead of the calendar and the midnight check never fires.

Old logs are yours to delete. tick.q rolls a new sym<date> every end of day and never removes old ones. Here every simulated day adds one, which is what the cleanup step's rm -f data/segment{0,1}/sym20* is for.

The blueprint trades memory for simplicity. Holding the IDB in RAM makes intraday queries fast without McCarthy's per-sym bookkeeping, but it's also why the IDB grows all day and why Community Edition's 16 GB cap limits BBO. Switching the WDB to sym-keyed int-partitions would remove the end-of-day sort.

McCarthy's disksort is the low-memory way to sort on disk. xasc loads the whole table. disksort computes one sort index, then rewrites one column file at a time. It does nothing if the sym column is already s#, and it skips any column whose first 256 values are identical. In his tests it was slower than xasc (20 s against 13 s for 100M rows), but it never holds the whole table in memory. That's the trade-off behind the "up to 4×" figure in rule 2, and he advises timing both on your own tables.

If you switch the WDB to sym-keyed int partitions, McCarthy's paper lists the traps:

  • Create an empty 0 partition first. Otherwise kdb+ can read a directory such as 2021 (a sym's enum index) as a year.
  • Symlink the HDB's sym file into the temp directory rather than copying it, so both enumerate against the same list.
  • Run .Q.chk and reload whenever a new sym or table appears, so every partition has every table.
  • Un-enumerate the sym column of the on-disk rows before joining them with memory. Otherwise the result mixes type 20 and type 11 sym columns.
  • Don't append the # files that hold string and list column lengths. They're rebuilt in the HDB partition.
  • Rewrite .d so sym comes before time, as HDB tables expect.
  • Keep LASTTIME per table and sym, so a query whose window starts after the last disk write skips the disk.

McCarthy benchmarked 10 FX syms. With thousands of equity syms, his design means thousands of partition directories, and a flush touches many of them. The AquaQ workshop's merge-vs-sort chart is the source for "merging wins on low cardinality, sorting can win on high".

How Lag and Throughput Are Measured

Before each data batch, the feed publishes a batch_sent row carrying a batchId. The RDB's upd is wrapped by .met.instrument, and when the matching batch lands it publishes batch_arrived back through the TP. .gw.transitLag is arrived time minus sent time for each batch, which covers the feed → TP → RDB path.

.gw.throughput reports rows_per_sec (offered) and arrived_rows_per_sec (ingested). A dropped batch never gets an arrival, so a gap between the two means data is being lost.

q)gw(`.gw.transitLag;"n"$.z.p-0D00:01)      / n, avg/p50/p95/max µs per shard, table
q)gw(`.gw.throughput;0D00:00:15)            / sent vs arrived rows/s
q)r0:hopen 5011; r0"select count i by metric from metrics"
