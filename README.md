# Sharded Ticks, Segmented History

### Throughput & Latency in q/KDB+

*Trilogy [Part Three: Sharded Ticks, Segmented History — The Machine](https://rohanshiloh.github.io/tickerplant.ai/)*

**Read it here: [rohanshiloh.github.io/tickerplant.ai](https://rohanshiloh.github.io/tickerplant.ai/)**

A hands-on runbook for KX's [scalable ingestion blueprint](https://github.com/KxSystems/blueprints-scalable-ingestion): two tickerplant shards (A–M and N–Z), each with its own RDB, WDB and IDB, feeding one segmented HDB behind a shard-aware gateway. It runs on a single laptop with the free KDB-X Community Edition, opens one terminal tab per process, and then takes the stack apart lab by lab.

The whole document is one self-contained page, `index.html`.

## What's inside

| Part | What it covers |
|---|---|
| **How It Fits Together** | The processes, ports and data flow, with diagrams for sharding, the WDB → IDB hand-off and the end-of-day barrier |
| **Run It** | Clone, clean up, and start all eleven processes, with a Warp launch configuration and a plain-shell alternative |
| **The Five Rules** | AquaQ's rules for real-time kdb+ systems, and how the blueprint scores against each |
| **Labs A–K** | Sharding, the WDB and IDB, the segmented HDB, end of day, recovery, the memory cap, a CEP, driving `tick.q` and `u.q` by hand, and chained TPs |
| **Variants E+ to K+** | Changes the blueprint doesn't make, each run on a copy so the repo stays untouched: end-of-day sort workers, checkpointed WDB restarts with no duplicates, hard limits (`-w`, `-T`, `-g`), recovering a CEP without the log, and an async gateway |
| **Production Patterns** | Splitting tickerplants, where the end-of-day write happens, compression, tiered storage, gateways at scale, disaster recovery, access control, discovery and monitoring |
| **Throughput & Latency** | A 30-second stats collector, then labs P1–P9: rows per message, logging cost, broadcast publish, timer mode, slow subscribers, memory-mappable logs and a deferred-sync log handshake |
| **Context, Comparisons & Practicalities** | Sharding by data source, TorQ's STP, three ways to write down intraday, tuning the load, Community Edition limits, disk usage, and running on kdb+ 4.1 |

## Requirements

- macOS. The launch configuration is for [Warp](https://www.warp.dev), and the plain-shell alternative works in any terminal
- KDB-X Community Edition, or kdb+ 4.1 with the changes noted in the document
- A clone of [KxSystems/blueprints-scalable-ingestion](https://github.com/KxSystems/blueprints-scalable-ingestion) at `~/Code/blueprints-scalable-ingestion`

The data is synthetic, generated by the blueprint's own feed, so no market data is needed.

## A note on the code

The blueprint's commands come straight from its repo. Much of the lab and variant code was written for this document and has **not been run**, so expect small fixes. Every variant writes only to a `variants/` folder and ends with a revert step.
